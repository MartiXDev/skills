# CancelOrder security contract

## Actor and authorization model

This is a design contract; no consuming application or Platform package version was provided, so names below are illustrative. The application should use a small provider-independent actor seam (for example, `ActorContext`) containing a verified subject ID, authentication state, tenant/scope, and mapped permissions. The request must never supply the actor ID, customer ID, role, or authorization decision.

The authorization rule is:

```text
allow = same authorized scope AND
        ((actor has orders.cancel.self AND actor.subjectId == order.customerId)
         OR actor has orders.admin)
```

`orders.admin` is an explicit permission, not merely a client-supplied role string. In a multi-tenant system it must be explicitly tenant-scoped or global; it must not imply cross-tenant access accidentally. In a single-tenant system it permits any order.

| Caller | Result | Business effect |
| --- | --- | --- |
| Unauthenticated | Endpoint policy returns 401 | The operation is not invoked; no mutation, Outbox row, or successful audit event |
| Authenticated without the cancellation capability | Endpoint policy returns 403 | The operation is not invoked |
| Customer with `orders.cancel.self`, owning the order | Operation allows | Continue to state and persistence checks |
| Customer with `orders.cancel.self`, not owning the order | Operation denies (403, or 404 to avoid order enumeration) | No mutation or Outbox event |
| Administrator with `orders.admin` in the authorized scope | Operation allows any order in that scope | Continue to state and persistence checks |

## Endpoint and operation checks

Use an explicit named endpoint policy, such as `orders.cancel.request`, on `POST /orders/{orderId}/cancel`. The policy should require an authenticated, verified principal and either the self-cancellation capability or `orders.admin`. It is deliberately a coarse gate: it cannot establish ownership from route metadata alone.

The Minimal API endpoint remains thin: bind `orderId` (and any transport request data), obtain the actor and correlation context, invoke the explicitly registered internal sealed `CancelOrderOperation`, and map its typed result to the documented HTTP/Problem Details contract. It must not perform the state transition or trust claims copied into the request.

`CancelOrderOperation` repeats the security decision before any business mutation:

1. Reject a missing/invalid actor context.
2. Load only the order data needed for scope, ownership, status, and the concurrency token. Apply the scope predicate in the query.
3. Evaluate `owner + orders.cancel.self` or `orders.admin`; do not rely on the endpoint having run.
4. Only after authorization passes, check whether the order is cancellable and apply the cancellation.

This second check protects direct operation calls, future endpoints, jobs, and confused-deputy paths. An endpoint-policy denial must fail before the operation is called and therefore cannot create a successful `CancelOrder` audit event. If denied attempts are required by the threat model, record a separate `orders.cancel` audit decision with outcome `denied`; it is never a business-success event.

## Immutable audit event contract

A successful cancellation writes one server-created, append-only security audit record. The event is immutable after insertion and is not built from client input.

| Field | Contract |
| --- | --- |
| `eventId` | Unique immutable ID generated by the application; also useful for reconciliation/idempotency |
| `schemaVersion` | Version of this audit shape |
| `actorId` | Stable verified subject identifier; use a pseudonymous ID where policy requires it, not an email address |
| `authorizationBasis` | `owner` or `orders.admin` (and, where applicable, the scope/tenant) |
| `actionCode` | Stable application-owned code such as `orders.cancel` |
| `outcome` | `succeeded` for the committed cancellation; denied/rejected/failed are separate outcomes when those attempts are audited |
| `targetType` | `order` |
| `targetId` | Order identifier |
| `occurredAtUtc` | Server-generated UTC timestamp, not a client timestamp |
| `correlationId` | Request/trace correlation identifier |
| `causationId` | Optional command/idempotency identifier for replay reconciliation |
| `tenantId` | Required only when the application's tenant model needs it |
| `reasonCode` | Optional bounded, non-PII application code; never raw free text by default |

The record must not contain tokens, credentials, provider secrets, unnecessary PII, raw exception text, or an untrusted actor/target description. Restrict audit writes and reads, apply retention/backup policy, and prevent application code from updating or deleting committed records. A tamper-evidence mechanism may be added only when the threat/compliance model requires it; it is not a substitute for the transaction.

## Persistence and failure behavior

The default choice is one module-owned database transaction and one `DbContext` boundary for the order update, durable audit row, and Outbox message:

```text
BEGIN
  authorize and read order
  update Order.Status = Cancelled and its concurrency token
  INSERT SecurityAuditEvent(outcome = succeeded, ...)
  INSERT OutboxMessage(type = OrderCancelled, stable event ID, ...)
COMMIT
return success only after COMMIT succeeds
```

No order update is committed without its audit row and `OrderCancelled` Outbox message. No audit success is committed without the order update. If the audit and order databases are different physical stores, do not claim a distributed atomic transaction: first atomically persist a local durable audit/outbox record with the order and use a monitored relay to the external audit store. The local record is then the source of truth; failure to persist that local record still blocks cancellation.

Because this contract treats the security audit as required evidence, audit persistence is **fail closed**:

| Failure | Contract |
| --- | --- |
| Audit insert unavailable, transaction rolls back, or commit fails | Do not cancel; do not enqueue Outbox; return a generic 503 Problem Details error such as `orders.audit.persistence-unavailable` and emit an operational alert/metric with the correlation ID |
| Outbox insert or order update fails | Roll back the audit and all other writes; return a typed dependency/concurrency failure, never partial success |
| Optimistic-concurrency conflict | Roll back; return 409 and no successful audit/Outbox pair |
| Request cancellation/timeout before confirmed commit | Roll back where possible and do not report success |
| Database connection is lost while commit outcome is unknown | Return an indeterminate dependency response, reconcile by `causationId`/`eventId` before retrying, and use a uniqueness constraint to prevent a duplicate cancellation event |

Do not write the audit asynchronously after committing the order, fire-and-forget it, or silently downgrade to a log. A bounded retry may retry the whole transaction, subject to the request deadline; it must not retry only the order update. Outbox delivery remains an observable at-least-once process, so consumers need durable deduplication and idempotent effects. The Outbox integration event, domain event, application log, and security audit record are separate contracts.

## Threat model and observability

- **IDOR/order enumeration:** enforce ownership and scope in the operation, not only in endpoint claims; return 404 for a non-owner when hiding resource existence is required.
- **Privilege escalation or forged identity:** derive actor context from the authenticated provider adapter, map claims to explicit permissions, and recheck in the operation. Never accept an actor ID or admin flag from the body or route.
- **Replay and races:** use an idempotency/causation ID where commands can be retried, an application-managed concurrency token, and a unique Outbox/audit event ID. Define whether an already-cancelled order is an idempotent success without creating a second Outbox event.
- **Audit loss/tampering:** keep the append-only audit store durable, access-controlled, backed up, and alert on write failure or unavailable readiness dependencies.
- **Sensitive-data leakage:** logs and Problem Details contain only bounded error codes, outcome, route, and correlation context; redact tokens, emails, raw provider errors, and free-form order data.

Structured logs, traces, metrics, health/readiness signals, transaction rollback tests, and Outbox backlog metrics support diagnosis, but logs are not an audit trail. Required evidence includes host tests proving 401/403 requests do not invoke the operation, operation tests for owner/admin/other-tenant decisions, immutable-field and PII checks, and real-provider tests proving rollback when audit or Outbox persistence fails, concurrency behavior, and recovery from an uncertain commit. InMemory or SQLite tests alone cannot prove those transaction and provider guarantees.
